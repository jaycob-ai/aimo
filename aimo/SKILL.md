# AIMO

## 工作目录

在当前对话所在的项目目录中工作，不写死任何本地绝对路径。这样同一份 Skill 可以放在任意目录、任意机器上使用。

- 用户提供了目录、文件或链接时，以用户提供的为准。
- 用户没有指定时，使用当前项目根目录，并按下方“数据文件”就地读写。
- 找不到数据文件时，先向用户确认项目位置；确认后再初始化，不要自行在其他目录新建一套项目。
- 不要修改技能目录内的文件来代替项目数据。

## 命名约定

本 Skill 统一使用 **AIMO** 作为名称、触发词和标题。

项目里的数据文件与文件夹按各自项目的既有命名，不要为了统一称呼而重命名。下文出现的文件名均为默认值，用户指定了别的名字时以用户的为准。

## 唯一职责

只执行一条流程：检索与核验 → 展示候选 → 等待确认 → 写入本地 Markdown → 回读验收。

- 只产出本地的 Markdown 记录，不依赖任何云端服务、数据库或站点部署。
- 不整理或写入知识点。
- 不做网站开发、前端改动、构建或发布。

## 启动规则

- 用户说“AIMO”时，只执行检索、核验和候选内容展示，不写入文件、不更新数据库、不生成网页。
- 用户看完候选内容后，只有明确说“加入”“写入”“更新”“采用”或同等含义时，才执行相应写入操作。
- 用户只说“继续”“连接”或“打开链接”时，不得推定为同意写入；继续展示或提供链接即可。
- 每日新闻与知识点严格分开：本 Skill 不得生成、提炼或写入知识点。
- 用户提供文章或链接时，以该内容为输入继续整理流程。
- 涉及当天新闻、人物言论、产品、论文或工具时，联网核验发布日期、事件发生日期和原始出处。
- 优先引用官方公告、论文、项目仓库等一手来源；媒体报道作为补充。

## 数据文件

所有数据以 Markdown 为准，只在本地产出，不写入数据库或云端：

- `AI行业进展.md`：公司/机构数据库与行业进展
- `每日热点.md`：每日新闻、论文、工具与人物观点的流水记录

- 首次运行时检查这两个文件；缺失时按“格式规范”初始化。
- 已有文件必须原位增量更新，不覆盖用户历史内容。
- 用户指定了其他文件名或目录时，以用户指定的为准。

## 每日信息更新

### 1. 获取内容

根据用户请求选择：

- 日常运行固定扫描“前一个自然日”在公开信息流中出现的内容；以 `Asia/Shanghai` 的 00:00–23:59 为边界。例如 8 月 23 日执行时，只整理 8 月 22 日这期新闻。
- 读取用户提供的文章、链接或材料。

日常运行的目标是形成用户每天阅读的一期新闻，而不是考据式重建所有事件的首发时间。候选和写入记录的日期统一使用“新闻期次日期”（即被扫描的前一个自然日）。来源实际发布日期如与新闻期次不同，只在摘要中简短说明，不因此把条目移出当期，也不主动回填历史日期。

只有用户明确说“候补”“补录”“放到对应日期”或同等含义时，才进入补录模式：核验事件实际发生或官方发布的日期，并将该条内容写入对应历史日期。不得自行把日常扫描变成历史补扫。

自动检索必须覆盖五个维度：

1. 行业新闻：公司发布、融资、政策、基础设施和产业进展。
2. 人物账号：逐个检查下方“人物监控名单”的官方账号或可核验原始访谈，不只依赖媒体转述。
3. 开源项目：发现 GitHub 高星、近期增长快、版本仍活跃且有实际用途的项目。
4. AI 工具与应用：编程 Agent、办公 Agent、研究与论文工具、设计工具、CLI、开源应用、效率工具和热门模型。
5. 论文：单独检索 Agent、大模型、具身智能和评测相关的新论文，不把论文混在普通产品新闻里处理。

#### 开源模型监控

保留上述通用信息源，另外执行“机构白名单 + 跨平台追踪 + 增量检测”，不得只检索新闻关键词或 GitHub 新仓库。

每日逐个检查以下机构的官方网站、GitHub Organization、Hugging Face Organization、官方 X/公众号和 arXiv 作者/机构动态：

- OpenMOSS、Qwen、DeepSeek、OpenBMB、Moonshot AI、MiniMax、StepFun、Zhipu AI
- Tencent Hunyuan、ByteDance Seed、Baidu、NVIDIA、Meta、Google DeepMind
- Mistral AI、Liquid AI、Nous Research
- Physical Intelligence、Figure、1X、智元机器人、银河通用等重点具身团队

对每个机构比较前一个自然日的跨平台增量，重点识别：

- 新仓库、Release、Tag、checkpoint、Collection、Space 或模型卡变更
- 新权重、新参数版本、新模态、量化/GGUF/MLX 版本
- 训练、微调、推理代码或数据集首次开放
- vLLM、SGLang、llama.cpp 等推理框架的正式支持
- 许可证、商用条件、Preview/GA 状态变化

旧仓库出现新权重、代码、数据或许可证变化时，视为新的开源事件。不得仅以仓库创建日期或论文首发日期判断是否有新增。

日常只执行一个时间窗口：前一个自然日 00:00–23:59（Asia/Shanghai）。不自动补扫最近 7 天，不因来源首发时间较早就排除前一日重新进入信息流、获得重要更新或形成显著关注度的内容，但必须在摘要中说明真正的新信息是什么。

记录“新闻期次日期”与“来源发布日期”：日常候选与每日热点按新闻期次日期记录；来源发布日期用于事实核验，必要时写入摘要。只有用户明确要求补录时，才按实际事件日期回填历史记录。

完成候选清单前执行遗漏审计：确认国内外重点机构均已检查，GitHub 与 Hugging Face 均已覆盖，且没有遗漏旧仓库中的新权重、代码、数据、许可证或推理支持。

#### GitHub 项目筛选

每天同时检查 GitHub Trending 与关键词搜索，候选项目需满足以下条件中的多数：

- 星数处于同类项目前列，默认优先 `stars >= 1,000`；垂直新项目可降低门槛，但必须说明近期增长或行业影响。
- 最近 90 天仍有提交、Release 或维护者响应，避免只看累计星数收录停止维护的项目。
- README、许可证、安装方式和核心用途清楚，可实际运行或复现。
- 优先 Agent、模型推理、RAG、研究/论文、数据处理、自动化、开发者工具、评测和多模态项目。
- 去除刷星嫌疑、镜像仓库、纯教程合集、重复封装和无有效代码项目。

每个入选项目记录：仓库名、用途、当前星数、近期开发表现、许可证、适用人群、关联公司/组织、仓库链接。星数是动态数据，必须标注检索的绝对日期，不写成永久事实。

#### 实用工具筛选

工具以“能帮助用户完成明确任务”为核心，不按宣传热度收录。优先能直接试用、价格和隐私说明清楚、有文档或真实用户反馈的工具。覆盖：

- 编程与 Agent
- 论文阅读、翻译、分栏、笔记与问答
- 搜索、知识管理与办公自动化
- 图像、视频、音频和设计
- 数据分析、模型部署与评测

每项说明具体解决什么问题、典型用法、平台、价格/开源状态、数据隐私注意点、关联公司和官方链接。相同能力只保留更成熟或更有差异化的代表工具。

检索工具时组合使用 Agent、CLI、Copilot、Cursor、Replit、Bolt、v0、Devin、WorkBuddy、Claude Code、Grok、开源工具、AI 应用、效率工具等关键词。

#### 论文检索与分类

每天单独检查前一个自然日进入信息流的新论文与热门论文，优先论文原文、作者项目页、代码仓库和正式评审页面。论文至少归入一个主分类：

- `Agent`：规划、工具调用、多智能体、长程任务、记忆、Agent Harness 和环境交互。
- `大模型`：LLM 架构、训练、推理、对齐、数据、长上下文、效率和模型能力研究。
- `具身智能`：机器人、VLA、世界模型、I2V world model、仿真、控制、导航和真机迁移。
- `评测`：Benchmark、评估方法、模型裁判、可靠性、安全测试、Agent/机器人能力测量。

允许增加一个次分类，但必须指定唯一主分类。写入每日热点时保持类型为 `paper`，并在论文标题前添加主分类，例如 `【Agent】论文标题`、`【具身智能】论文标题`，便于按分类检索。对每篇论文说明：研究问题、核心方法、关键实验结果、局限、作者机构、代码/项目地址、主分类和关联公司。没有可靠实验或只有营销摘要时不收录。

### 2. 总结并呈现候选项

对每项提炼：

- 谁发布了什么
- 关键数字或事实
- 为什么重要
- 新闻期次日期；如来源实际发布日期不同，在摘要中注明
- 来源链接
- 建议归类
- 关联公司

合并重复报道，区分“新闻期次日期”和“来源实际发布日期”，不把未经证实的说法写成事实。日常候选归入前一个自然日；只有补录模式才按事件实际日期回填。先向用户展示精简候选清单。

默认按以下阅读格式完整展示，不先写入：

1. 使用前一个自然日的绝对日期作为当期标题。
2. 每个候选项单独成节，包含标题、事实摘要、关键数字、实际价值、关联公司和原始来源。
3. GitHub 项目额外说明星数及检索日期、当日增长、许可证、适用场景和注意事项；达到高星门槛的项目标记为 `GitHub 高星`，便于快速识别重点项目。
4. 最后给出“今日结论”，提炼最值得关注的两个到三个方向；结论仍属于新闻摘要，不自动转成知识点。
5. 明确说明哪些监控维度在前一个自然日没有可靠新增；没有人物观点、论文或行业新闻时直说，不用历史内容补齐。
6. 结尾询问用户要加入哪些内容，可让用户回复编号、名称或“全部加入”。

候选展示阶段属于只读阶段。即使候选项质量很高，也不得提前修改任何数据文件。

### 2.1 建立公司关联

新闻和论文写入前，必须关联一个或多个公司实体。

执行以下规则：

1. 先在 `AI行业进展.md` 中匹配已有公司，统一使用公司表中的标准名称。
2. 将产品发布、融资、合作、政策影响、人物言论和工具归属关联到直接相关公司。
3. 将论文关联到作者所属公司、发布机构、模型或项目的维护公司；多个公司共同参与时全部记录。
4. 区分品牌、产品和公司：例如将产品名保留在标题中，将“关联公司”写为公司实体。
5. 子公司或研究院有独立公司记录时使用独立实体；没有时关联母公司，并在摘要中说明具体团队。
6. 使用 `/` 分隔多个公司，去重并保持公司数据库中的标准名称顺序。
7. 无法从可靠来源确认公司时，不得臆造；使用 `未关联`，并在候选清单中标记待确认。

写入前检查：除确实无法关联的宏观政策或纯学术条目外，“关联公司”不得为空。

### 3. 确认写入

必须先取得用户明确确认。不得将“AIMO”“看看”“继续”“连接”解释为写入授权。用户可以回复编号、名称、“全部加入”或明确指定目标文件与范围。

确认后再依次询问或合并询问：

1. 是否写入公司数据库
2. 是否写入每日热点

如果用户在看完候选内容后明确要求全部更新，不重复询问。

### 4. 更新公司数据库

写入 `AI行业进展.md`。

已有公司：更新对应行的“发布/要点”和“报道链接”，避免重复信息。

当新闻、论文或知识点关联到尚未收录的公司时，先确认该公司名称、官网和分类，再新增公司记录。不要为了满足关联要求创建无法验证的公司。

新公司：按以下分类添加：

- 传统大厂：科技、制造、互联网巨头
- 大模型厂商：主营基座模型或 LLM
- 具身智能厂商：机器人、世界模型、VLA、机器人零部件
- AI Infra：芯片、算力、网络、数据中心基础设施
- 云服务/平台：云计算、MLOps、数据服务、SaaS 工具
- 汽车：自动驾驶、车载 AI、车规芯片
- 初创 Agent 公司：以 AI Agent 为核心产品的初创公司
- 行业/政策动态：不适合归入公司的政策与产业事件

公司表格行格式：

`| 公司 | 官网 | 发布/要点 | 报道链接 |`

### 5. 更新每日热点

写入 `每日热点.md`。

表格格式：

`| 日期 | 新闻 | 类型 | 关联公司 | 要点 | 链接 |`

类型只允许：

- `product`
- `paper`
- `industry`

同一事件已存在时更新原行，不追加重复行。

“关联公司”必须使用公司数据库中的标准名称。论文同样写入本表并使用 `paper` 类型，同时填写作者机构或发布主体对应的公司；多家公司以 `/` 分隔。

### 6. 写入与验收

用户确认写入后，按以下顺序完成：

1. 按“格式规范”写入或更新 `AI行业进展.md` 与 `每日热点.md`。
2. 检查去重、日期、类型、来源和公司关联是否完整。
3. 重新读取修改过的段落，确认 Markdown 表格结构、字段数量和转义没有损坏。
4. 向用户报告新增数量、条目、来源和公司关联；写入失败时保留原有内容并说明具体环节。

本 Skill 到写入本地 Markdown 为止，不涉及云端数据库、接口、前端构建或站点部署。

## 固定口令

- `AIMO`：只检索、核验并展示每日候选，不写入。
- `全部加入`：仅将当前已展示并确认的每日候选写入本地数据文件，不加入知识点。

## Markdown 格式规范

### AI 行业进展

标题固定为 `# AI行业进展`，并保留这些二级分类：

- 传统大厂
- 大模型厂商
- 具身智能厂商
- AI Infra
- 云服务/平台
- 汽车
- 初创Agent公司
- 行业/政策动态

公司分类表头：

`| 公司 | 官网 | 发布/要点 | 报道链接 |`

行业/政策表头：

`| 事件 | 要点 | 链接 |`

### 每日热点

标题固定为 `# 每日热点`，表头为：

`| 日期 | 新闻 | 类型 | 关联公司 | 要点 | 链接 |`

## 质量要求

- 不删除用户笔记、历史条目或页面功能。
- 所有事实性新增内容保留可访问来源。
- 使用绝对日期，避免“今天”“昨天”造成历史歧义。
- 表格单元格中的竖线和换行必须正确转义。
- 写入前检查重复项、分类和字段数量。
- 检查新闻和论文的关联公司是否存在于公司数据库；允许 `未关联`，但必须说明原因。
- 检查同一公司的中文名、英文名、品牌名和子公司名没有被误拆成重复实体。
- 修改后重新读取相关段落，确认 Markdown 表格未损坏。
- 写入失败时保留原有内容，并报告具体原因。
